# Frontend Business Logic and Atlas Read-Model Audit

Audit date: 2026-06-07

Scope: checklist frontend, API read paths, local worker offload paths, and MongoDB Atlas preparation needed to make frontend views consume simple, production-ready DTOs instead of running business logic in client components.

## Executive Summary

The frontend is functionally rich but still carries too much orchestration, derived state, polling, optimistic reconciliation, and product/business branching inside client components. The repo already has the right architectural direction: `IntelligenceSnapshot.webappProjection` in MongoDB Atlas is generated by the local snapshot worker and consumed by lightweight APIs such as company dashboard, nav, planning summary, sales summary, and blocks summary.

The highest-value improvement is to expand that projection pattern into a set of per-company, per-surface read models that are generated locally and stored in Atlas. The frontend should render GDS-only view DTOs and send intent/actions; it should not sort, classify, derive operational state, evaluate capability diffs, or compose multi-endpoint views.

## Existing Strengths

The codebase already contains the correct foundation:

- `IntelligenceSnapshot.webappProjection` stores prepared Atlas JSON per company.
- `scripts/lib/intelligence-snapshot.js` builds counts, home charts, planning summary, nav counts, top tasks, sales summary, and miniapp attention counts.
- `src/lib/company-read-model.ts` normalizes projection payloads for server APIs.
- Summary APIs already consume projection data:
  - `src/app/api/companies/[companyId]/dashboard/route.ts`
  - `src/app/api/companies/[companyId]/nav/route.ts`
  - `src/app/api/companies/[companyId]/planning-summary/route.ts`
  - `src/app/api/companies/[companyId]/sales-summary/route.ts`
  - `src/app/api/companies/[companyId]/blocks/summary/route.ts`
- Local snapshot worker already refreshes missing/dirty projections.

This means the recommended path is evolutionary: extend the existing projection/read-model architecture, not replace it.

## Main Problems

### 1. Client Components Own Too Much Business Logic

Problem examples:

- Settings page computes module/package diffs, capability previews, daemon policy state, and transaction readiness.
- Unit board computes visible items, reconciliation, optimistic creation/update/move state, retries, and board scope behavior.
- Rulebook runner executes a multi-step state machine through many browser-triggered endpoints.
- Local AI page derives operational labels and incident state from raw command-center payloads.
- Data page coordinates ingestion, files, sources, enrichment, and refresh actions from the browser.

Impact:

- Larger client bundles.
- More hydration work.
- More browser CPU on low-power devices.
- Harder accessibility state management.
- More duplicated error/retry logic.
- More network round trips from the browser.

### 2. Many APIs Return Operational Records Instead Of View DTOs

Several endpoints expose domain records or broad objects and rely on the frontend to make them presentable. The target should be:

```ts
type SurfaceReadModel<TItem, TAction = string> = {
  contractVersion: number;
  generatedAt: string;
  companyId: string;
  surface: string;
  freshness: {
    status: "FRESH" | "AGING" | "STALE" | "MISSING";
    ageMinutes: number | null;
  };
  summary: Record<string, number | string | boolean | null>;
  filters: Array<{ key: string; label: string; count: number; selected?: boolean }>;
  columns?: Array<{ key: string; label: string; count: number; itemIds: string[] }>;
  items: TItem[];
  actions: Array<{
    key: TAction;
    label: string;
    enabled: boolean;
    disabledReason?: string;
    confirm?: { title: string; body: string; destructive?: boolean };
  }>;
  observability: {
    sourceRunId: string | null;
    inputWatermark: string | null;
    checksum: string | null;
  };
};
```

The frontend should render this contract and send action intents. It should not decide what a failed mission means, which retry action is safe, or how a capability package changes downstream jobs.

### 3. Polling Is Too Browser-Heavy

There are 35 client timers. Some are valid for operator surfaces, but most should be replaced by one of:

- Server-prepared summary with stale/fresh metadata.
- Local status/read-model endpoint that changes only when worker progress changes.
- Event log cursor polling with `since`/`cursor`, not full payload reload.
- Server-Sent Events only for active operator consoles.

### 4. MongoDB Atlas Is Used As Source Store More Than Read Store

Atlas has strong indexing already in the Prisma schema, but the frontend-facing shape is still under-materialized. Current `webappProjection` proves the pattern but does not yet include enough surface-specific read models for heavy pages.

Target: Atlas should hold frontend-ready documents that are small, indexed, and versioned by surface.

## Recommended Atlas Read-Model Architecture

### Option A: Extend `IntelligenceSnapshot.webappProjection`

Use this for low-cardinality summaries:

- nav
- dashboard
- planning summary
- sales summary
- miniapp attention counts
- top tasks
- shell capability metadata

Pros:

- Already implemented.
- One read per company.
- Simple freshness model.

Cons:

- Can become too large if it starts holding boards, review queues, or operational logs.

### Option B: Add Dedicated `CompanySurfaceProjection` Collection

Recommended for heavier surfaces.

Suggested Prisma model:

```prisma
model CompanySurfaceProjection {
  id             String   @id @default(uuid()) @map("_id")
  companyId      String
  surfaceKey     String
  contractVersion Int
  generatedAt    DateTime
  inputWatermark String?
  checksum       String?
  freshness      String   @default("FRESH")
  payload        Json
  itemCount      Int      @default(0)
  staleAt        DateTime?
  createdAt      DateTime @default(now())
  updatedAt      DateTime @default(now()) @updatedAt

  company        Company  @relation(fields: [companyId], references: [id], onDelete: Cascade)

  @@unique([companyId, surfaceKey, contractVersion])
  @@index([companyId, surfaceKey, updatedAt])
  @@index([surfaceKey, freshness, staleAt])
}
```

Recommended surfaces:

- `settings.capabilityControl`
- `unitBoard.project`
- `localAi.commandCenter`
- `knowmore.reviewQueue`
- `data.ingestionOps`
- `pipeline.queue`
- `sales.opportunityBoard`
- `destination.rulebookRunner`
- `destination.reviewWorkspace`
- `observability.runtime`

### Option C: Add `CompanySurfaceItemProjection` Collection

Recommended only for boards/lists that can exceed safe JSON document size or need pagination.

Suggested shape:

```prisma
model CompanySurfaceItemProjection {
  id              String   @id @default(uuid()) @map("_id")
  companyId       String
  surfaceKey      String
  itemId          String
  columnKey       String?
  orderRank       Float?
  searchText      String?
  filterKeys      String[] @default([])
  payload         Json
  payloadChecksum String?
  updatedAt       DateTime @default(now()) @updatedAt

  @@unique([companyId, surfaceKey, itemId])
  @@index([companyId, surfaceKey, columnKey, orderRank])
  @@index([companyId, surfaceKey, updatedAt])
}
```

Use this for:

- Unit boards.
- Opportunity boards.
- Review queues.
- Source/file ingestion rows.
- Mission candidate lists.

## MongoDB Atlas Improvements

Use Atlas as a prepared read layer:

1. Create materialized read documents for frontend surfaces.
2. Keep raw workflow/source records separate from UI DTOs.
3. Add compound indexes that match API access patterns.
4. Keep projection payloads bounded; split large item lists into item projection documents.
5. Use freshness metadata so UI can show stale/refreshing states without recomputing.
6. Store display-ready labels, counts, safe actions, disabled reasons, and severity.
7. Store server-derived `sortKey`, `filterKeys`, `searchText`, and `columnKey`.
8. Prefer `select` projections in Prisma/API routes so only needed fields leave Atlas.
9. Use Atlas Performance Advisor and slow query logs to validate high-volume routes.
10. For text-heavy source search, consider Atlas Search indexes with stored source for fields that can be served directly from the search index.

Relevant official MongoDB guidance:

- Atlas index management: https://www.mongodb.com/docs/atlas/atlas-ui/indexes/
- MongoDB performance tuning: https://www.mongodb.com/docs/manual/administration/performance-tuning/
- Atlas Search performance: https://www.mongodb.com/docs/atlas/atlas-search/performance/
- Atlas Search query performance and stored source: https://www.mongodb.com/docs/atlas/atlas-search/searching/

## Local Worker Offload Plan

### Snapshot Worker

Current role: builds `IntelligenceSnapshot.webappProjection`.

Expand it to:

- Rebuild dirty `CompanySurfaceProjection` records.
- Track projection dependencies by surface.
- Write `generatedAt`, `inputWatermark`, `checksum`, `recordCount`, and `staleAt`.
- Defer heavy recomputation when local memory is constrained.

### Foreground Worker

Current role: queue-owned mutation lane.

Keep it focused on:

- Product mutations.
- Pipeline jobs.
- Action execution.
- Marking affected surface projections dirty after writes.

### Status/Snapshot Workers

Use them to prepare:

- Local AI command center summary.
- Runtime incident list.
- Managed service health DTOs.
- Lane-event cursors and deltas.

Frontend should fetch:

```ts
GET /api/local-ai/command-center?cursor=...
```

not raw status plus raw lane events plus client-side derived state.

Current issue:

- 1353-line client component.
- 11 fetches.
- Capability package preview and transaction logic are mixed into rendering.

Move to server/local:

- Precompute capability package matrix.

- Precompute affected miniapps, blocked operations, and pipeline side effects.

Frontend target:

- Render form state.
- Send `preview` or `apply` action.
- Display server-provided diff and confirmation copy.

### 2. Local AI Page

Current issue:

- UI derives operational meaning from raw status payloads.
- Polls status and lane events every 5 seconds.

Move to server/local:

- Build `localAi.commandCenter` DTO in status server or a local API adapter.
- Include incident severity, safe actions, active task, lane events, and freshness.
- Use event cursor polling.

Frontend target:

- Render GDS operation state.
- Poll a single lightweight endpoint or subscribe only while visible.

### 3. Unit Board

Current issue:

- 46 hooks, optimistic reconciliation, board scope, retry, timeout, filtering, and move behavior in UI.

Move to server/local:

- Store board columns, item IDs, item payloads, filter counts, and allowed actions in `CompanySurfaceProjection` plus `CompanySurfaceItemProjection`.
- Server returns a board DTO with revision token.
- Mutations return action receipts and the next changed items/columns.

Frontend target:

- GDS board rendering and drag/drop only.
- No full board reconciliation logic after every action.

### 4. Rulebook Runner

Current issue:

- 12 fetches and many mission state transitions from the browser.

Move to local:

- Replace step-specific browser calls with a command endpoint:

```ts
POST /api/destination-missions/runs/:id/actions
{ action: "DISCOVER" | "EXTRACT" | "SCORE" | "PREPARE" | "EXECUTE_NEXT" | "EXECUTE_UNTIL_BLOCKED" }
```

- Local worker executes the state machine.
- API returns a receipt and the read-model projection updates asynchronously.

Frontend target:

- Render mission state and send commands.
- No mission orchestration state machine in client.

### 5. Data Page

Current issue:

- 13 browser fetches across files, sources, ingest, and enrichment.

Move to server/local:

- Create `data.ingestionOps` read model:
  - source/file counts
  - recent ingest jobs
  - blocked/error rows
  - upload state
  - safe actions
  - enrichment status

Frontend target:

- Render prepared sections.
- Upload or trigger action only.

### 6. Knowmore / Review Workspaces

Current issue:

- Review logic, polling, state transitions, and queue presentation are client-heavy.

Move to Atlas:

- Store review queue DTOs by surface and status.
- Include normalized evidence, correction prompts, safe action set, and accessibility-ready state labels.

Frontend target:

- Render list/detail.
- Send accept/decline/correction action.

### 7. Nav and Dashboard

Current issue:

- Already partly solved by `webappProjection`, but still polling and fetching from client.

Move to server:

- Hydrate nav counts and company shell state in server layout/page data.
- Use freshness metadata instead of frequent client refetches.

Frontend target:

- Client nav receives initial DTO and only refreshes on explicit invalidation or low-frequency visibility-aware polling.

## API Contract Direction

Create one read endpoint family:

```txt
GET /api/companies/:companyId/surfaces/:surfaceKey
```

Response:

```ts
{
  ok: true;
  projection: SurfaceReadModel<unknown>;
}
```

Create one action endpoint family:

```txt
POST /api/companies/:companyId/surfaces/:surfaceKey/actions
```

Request:

```ts
{
  action: string;
  targetId?: string;
  payload?: Record<string, unknown>;
  projectionRevision?: string;
}
```

Response:

```ts
{
  ok: true;
  receiptId: string;
  status: "ACCEPTED" | "APPLIED" | "REJECTED" | "CONFLICT";
  message: string;
  nextProjection?: SurfaceReadModel<unknown>;
}
```

This makes the UI simple and predictable: read DTO, render DTO, send action, receive receipt.

## Compatibility and Frontend Load Reduction

Keep these constraints:

- UI remains 100% GDS-only.
- Client components should only own interaction state, focus state, transient form input, and GDS rendering.
- No direct domain classification in client components.
- No browser-side sorting/filtering for primary business order. Server can still allow local cosmetic filtering over small lists.
- No multi-endpoint fanout from one client view unless the endpoints are independently visible widgets.
- All polling must be visibility-aware and cursor/delta-based.
- Read-model DTOs must include accessibility labels and state descriptions so components do not derive them.

Expected load reduction:

- Remove 30-50% of client fetch calls by replacing multi-endpoint views with single surface DTO endpoints.
- Reduce hydration complexity in the top 10 client files by splitting them into server data loaders plus smaller GDS client islands.
- Reduce browser polling from full payload refresh to cursor/delta refresh for operational surfaces.
- Reduce Atlas query fanout by replacing live aggregation on page load with materialized projections.

- No client view performs more than 3 direct fetches on initial load.

- UI receives display-ready labels, state descriptions, safe actions, disabled reasons, and freshness metadata.

- Production build remains clean.
- GDS boundary audit remains passing.

## Risks

- Projection payloads can become too large if item lists are embedded in a single JSON document.
- Stale projection behavior must be explicit or operators will distrust the UI.
- Mutation/read-model consistency needs revision tokens or action receipts to avoid confusing optimistic state.
- Too many indexes can increase write cost; Atlas index changes should be validated with real query patterns and Performance Advisor.
- Atlas Search should be used for text/source search, not as a replacement for normal indexed status/board queries.
