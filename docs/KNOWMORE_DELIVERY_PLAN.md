## Objective

Deliver a new `knowmore` experience in the online check Webapp that exposes AI-maintained flashcards built from:

- user-provided data sources,
- agent-discovered online sources,
- local AI enrichment and continuous refinement driven by checklist feedback.

The system must stay reliable when the online app and the local AI stack are temporarily disconnected. The local AI remains the source of enrichment and synthesis. The webapp remains the source of user interaction, visibility, and feedback capture.

This delivery plan is now complemented by:

- `docs/CONTINUOUS_IMPROVEMENT_PLAN.md`

That document defines how already-generated flashcards and downstream tasks should be revisited and improved over time using oldest-modified-first selection, business-value ranking, and bounded research.

## Product Definition

### User-visible behavior

- A new page exists at `/:companyId/knowmore`.
- The page lists flashcards.
- Each flashcard represents one knowledge slice that can support one or more checklist / NBA items.
- A flashcard shows:
  - public readable numeric ID,
  - UUID,
  - title,
  - concise body,
  - confidence,
  - impact,
  - weight,
  - freshness / last-updated information,
  - linked source references.
- A flashcard may be linked to multiple sources.
- Agent-found sources also appear on the Data page with a visible `found by agents` chip.
- All data entities exposed to users have:
  - UUID for internal stability,
  - public integer ID for readable references and auditability.

### System behavior

- Local agents ingest user-entered sources and agent-found sources.
- Local agents normalize, deduplicate, merge, score, and refresh flashcards.
- NBA / checklist actions feed back into local flashcard scoring and revision.
- Flashcards retain provenance so the system can explain why a flashcard exists and what sources support it.
- Flashcard merges do not destroy lineage.

## Reliability Principles

1. Source provenance is immutable
   - never lose the original source row, URL, or source type.
   - preserve citation snapshots so a flashcard can still explain its evidence after the source changes.
2. Flashcards are versioned
   - updates create a new revision or tracked refresh metadata instead of silent destructive rewrites.
3. Public numeric IDs are stable
   - once assigned, never recycled.
4. Online and local layers are loosely coupled
   - the online app must keep working if local sync is delayed.
   - the local stack must catch up from persisted state.
5. Feedback loops are explicit
   - accept / decline / comment actions must be traceable to the flashcard refresh that consumed them.
6. Merge logic is auditable
   - a merged flashcard must still show all contributing sources.
7. Conflicts are visible
   - contradictory sources must reduce certainty or enter review states instead of being silently merged.
8. Operators can repair the system
   - stale jobs, broken provenance, and bad merges must have explicit repair and reprocess paths.
9. Users can correct the knowledge layer directly
   - NBA feedback is not sufficient on its own for source cleanup and flashcard trust.

## Proposed Domain Model

### Core entities

- `SourceRecord`
  - UUID
  - public integer ID
  - company UUID
  - source type: `product`, `customer`, `competitor`, `agent_found`, later extensible
  - origin: `user` or `agent`
  - canonical title
  - canonical body / snippet
  - optional external URL
  - discovery metadata
  - timestamps

- `Flashcard`
  - UUID
  - public integer ID
  - company UUID
  - title
  - body
  - confidence
  - impact
  - weight
  - status
  - freshness timestamp
  - last generated by
  - created / updated timestamps

- `FlashcardRevision`
  - UUID
  - flashcard UUID
  - revision number
  - title
  - body
  - confidence
  - impact
  - weight
  - generation reason
  - model / agent metadata
  - timestamps

- `FlashcardSource`
  - UUID
  - flashcard UUID
  - source UUID
  - relation role: `primary`, `supporting`, `merged_from`

- `CitationSnapshot`
  - UUID
  - source UUID
  - normalized URL
  - fetched title
  - fetched snippet
  - content hash
  - fetched at timestamp
  - optional archival metadata

- `FlashcardFeedbackLink`
  - UUID
  - flashcard UUID
  - feedback UUID
  - effect summary

- `FlashcardCorrection`
  - UUID
  - flashcard UUID
  - user UUID
  - correction type: `hide`, `wrong`, `pin`, `refresh_requested`
  - optional note
  - timestamps

### ID strategy

- Add a stable public integer ID to every user-facing entity.
- Use a single shared sequence / counter strategy or a dedicated `PublicId` allocator table so IDs remain unique, monotonic, and collision-free.
- Preserve existing UUIDs as the internal primary keys.

## Pipeline Design

### Inbound data

1. User creates or updates a source on the Data page.
2. The online app persists the source and its provenance.
3. A local sync event is queued or detected by the local poller.
4. Local agents fetch changed source records.

### Local AI processing

1. Normalize source content.
2. Resolve duplicates / near-duplicates.
3. Extract candidate knowledge slices.
4. Merge with existing flashcards where confidence is high enough.
5. Otherwise create a new flashcard.
6. Recompute confidence, impact, and weight.
7. Detect conflicting evidence and lower confidence or flag for review.
8. Persist revision, source links, and citation snapshots.
9. Rebuild or refresh downstream NBA candidates.

### Feedback loop

1. User accepts / declines an NBA item and optionally leaves a comment.
2. The feedback row is linked back to the originating flashcard(s).
3. Local agents re-score or revise affected flashcards.
4. Regenerated flashcards influence subsequent NBA generation.

### Direct correction loop

1. User hides a flashcard, marks it wrong, pins it, bans a source, or requests refresh.
2. The correction is persisted as a first-class event.
3. Local agents use the correction to suppress, revise, or prioritize affected flashcards and sources.
4. The pipeline records the resulting revision or status change explicitly.

## Webapp Surfaces

### New page

- Route: `src/app/[companyId]/knowmore/page.tsx`
- Displays:
  - flashcard list,
  - confidence / impact / weight badges,
  - source chips,
  - public ID and UUID,
  - freshness state,
  - merge count / multiple-source indicators.

### Data page additions

- Show public ID on each source item.
- Show provenance chip for `found by agents`.
- Support filtering user-entered vs agent-found records.

### API additions

- read endpoint for flashcards,
- detail endpoint for a single flashcard,
- source-to-flashcard relation endpoint if needed,
- refresh / regeneration trigger endpoint if the UI needs explicit refresh control.

10. User correction controls
11. Backfill, observability, and reliability hardening

## Acceptance Standard

The feature is done only when all of the following are true:

- the Data page shows both user-entered and agent-found sources with public IDs,
- the Knowmore page renders flashcards with provenance and scores,
- every flashcard can trace back to one or more source records,
- feedback on NBA items changes local flashcard state on the next processing cycle,
- public IDs are stable and readable across all new entities,
- the local pipeline recovers cleanly after downtime,
- contradictory evidence is visible and does not silently collapse into one claim,
- operators can reprocess or repair a company knowledge graph safely,
- users can directly correct bad flashcards or sources,
- operators can inspect failures and stale processing with explicit logs or metrics.
